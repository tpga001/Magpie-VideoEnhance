# 浏览器视频掉帧复查、对照与部署

日期：2026-09-30  
正式运行目录：`E:\Program Files\Magpie-Experimental-x64`  
当前安装版本：`0.6.9-frame-stability-vsync`（只增加 `Present(1)`）  
状态：已完成隔离 Edge 对照、部署 P1、安装目录功能复验和真实 Edge B 站播放验证；真实 Chrome 长时间播放仍待复验，尚未达到稳定 60 FPS。

## 结论

浏览器视频卡顿有客观依据。部署后，真实 Edge B 站页面持续增强播放时，原生输入约为 24.875 FPS；当前 XeSSFG 只支持 2×、最多插入 1 帧，理论上最多形成约 50 FPS 的输出节拍。该会话实际显示平均 46.089 FPS，远低于用户希望的 60 FPS。后续对同一视频的匿名 360p 码流逐帧探测确认了 25 FPS，且浏览器至 Host 的测试区间没有丢帧。它支持“该视频至少有 25 FPS 码流”的判断；登录状态下的 1080p 码流是否完全相同仍需单独确认。

此前真实 Chrome 稳定播放段中，Magpie 原生链路约每秒接收 28.0 帧；XeSSFG 约每秒提交 28.2 个输入、报告产出 56.5 个 SDK 输出。SDK 输出计数不等于屏幕实际显示帧数。两次真实播放的页面和采样段不同，不应把 28 FPS 与 25 FPS 的差异直接归因于浏览器或新版本。

针对显示节拍的 P1 `Present(1)` 有一致但有限的改善迹象。此前同一隔离样本的直接 PresentMon 对照显示，P0/P1 平均显示分别为 58.36/58.91 FPS，未显示提交分别为 2.36%/1.15%，超过 25 ms 的显示间隔分别为 2.62%/1.59%。本轮再次对照时，P1 的 SidePanel 整场会话显示平均与低帧指标优于 P0，但它的统计窗口包含测试设置与清理，不能当成正式 61 秒播放区间的精确显示成绩。P1 已作为可回退的小步更新部署；真实 B 站仍不足 60 FPS，不能把候选片源的改善等同于实际网页达标。

SidePanel 只提供整场会话汇总，包含启动、画面建立和结束后的时间；四次时长也不完全相同。它能支持趋势判断，不能用于声称 P1 的正式播放区间精确提升了 0.983 FPS。带 FrameTrace 的行有额外诊断开销，更不能单独归因于 XeLL 等待顺序。无 FrameTrace 的 XeLL 候选平均值仅比 P1 高 0.270 FPS，两个低帧指标反而略低，没有足够证据部署。

直接 PresentMon 在本轮因权限不足无法新采集，提权尝试没有形成有效记录，因此没有伪装成有效 CSV。隔离测试中的正式观察区间与 SidePanel 整场会话的边界已分别保留在原始 `result.json` 中。

## 真实 Edge B 站播放

在 Edge 默认用户配置中加载已部署的 `BrowserVideoExtension`，并打开扩展弹窗开关后，播放用户提供的 B 站视频 `https://www.bilibili.com/video/BV1YDem6VEzC/`。21:49:50 开始增强：原生日志记录 `BrowserDecodedFrame` 输入 1920×1080、RTX Video VSR 质量 4 处理到 3840×2160、XeSSFG MFG 2×，最大可插入帧数为 1。增强窗口实际仍限制在网页视频区域 `360,505,2901,1935`，没有把浏览器界面放大到全屏。

21:51 左右连续 45 秒的只读窗口采样中，45/45 次 Edge 均在前台，增强层均可见、来源为同一 Edge 窗口、没有置顶，区域坐标保持不变。21:53:21 视频暂停。SidePanel 为这段完整播放会话给出的实际显示汇总为 204.994 秒、9448 帧、平均 46.089 FPS、1% Low 15.768、0.1% Low 10.667。这是整场会话统计，可能包含建立和结束阶段，不应当作 45 秒窗口采样的显示指标。

同一原生日志中，21:50:05.797 为上传第 300 帧、媒体 PTS 15.520 秒；21:53:18.746 为第 5100 帧、PTS 208.480 秒。中间 4800 帧 / 192.960 秒媒体时间，约为 **24.875 FPS**；墙钟区间也约为 192.949 秒。该值是进入 Magpie 的实际帧率，尚不能单独证明原视频编码帧率就是 25 FPS。由于本会话 XeSSFG 最多 2×，这些输入即使全部理想显示，输出节拍也约为 49.75 FPS；SidePanel 看到的 46.089 FPS 还包含显示阶段及会话首尾影响。XeSSFG 日志中的累计 `frames` 是 SDK 输出事件计数，不能替代 SidePanel 的实际显示帧数。

随后以隔离候选运行真实 B 站页面的匿名 640×360 码流，Edge 在正式 30.082 秒窗口的 6/6 次状态采样中保持前台。`requestVideoFrameCallback` 记录 751 次回调；连续 750 个媒体 PTS 间隔**全部为 40 ms**，即该码流稳定 25 FPS。浏览器视频质量统计增加 752 帧、解码丢帧 0；relay 回调 751、提交 751、接收 752，节拍/复制/待处理/选中跳过均为 0，源回调缺口 0，队列/回压/Host 丢帧也均为 0。接收与回调累计计数相差 1 帧，不能将其解读为丢帧或凭空生成帧。此测试确认**匿名 360p 码流本身是 25 FPS，扩展传输没有把它从 30 FPS 降到 25 FPS**。先前登录状态 1080p 播放也观察到约 25 FPS 输入，但两种码流帧率相同仍是推断。测试脚本语法已校验；此隔离探测没有部署新运行版。

## 真实播放的待解问题

19:38:16–19:39:07 的 Chrome 会话中，上传帧从 1 到 1200，媒体 PTS 推进 42.800 秒，墙钟推进 42.831 秒，原生输入约 28.0 FPS。XeSSFG 的低频日志约为每秒 28.2 次输入提交和 56.5 个 SDK 输出。其间窗口尺寸稳定在 3518×1975，没有反复重建。共享纹理发布在 1440 次中有 18 次等待 GPU fence，部分批次的峰值为 60–144 ms。此前隔离样本的 116.7/200.0 ms 屏幕停顿也伴随相近的下一次 `Present` 空窗。这些是两类已观测现象，尚不能合并为一个根因。

浏览器扩展已有五秒统计，包括回调、提交、接收、复制、ACK、队列和回压，但旧 Chrome 会话的扩展控制台数据无法追回。现有正式原生日志也没有 Host 序号缺口记录。匿名 360p 码流已证实为 25 FPS，2× 的约 50 FPS 是这一路径的输出节拍上限；登录状态 1080p 和其他 30 FPS 片源仍需分别验证。实际显示还应独立检查，不能用 SDK 输出事件代替。

## 下一步验收

以已经确认的 25 FPS 匿名码流为单独场景，评估适合 25→60 的补帧倍率、显示节拍或其他算法，并比较画质、延迟及算力；当前 XeSSFG 2× 无法仅靠性能调优达到 60 FPS。登录状态 1080p 应先直接采集逐帧媒体 PTS，确认它是否也为 25 FPS，再复核 Chrome 用户配置。30 FPS 片源则作为另一场景验证，若浏览器回调接近 30 而原生输入明显更低，补齐 Host 序号和媒体 PTS 诊断以定位损失。若可取得有权限的 PresentMon CSV，再按正式播放区间的实际显示 FPS、未显示比例、超过 25 ms 的间隔及最长间隔评价；不能用 SDK 计数冒充屏幕帧率。
