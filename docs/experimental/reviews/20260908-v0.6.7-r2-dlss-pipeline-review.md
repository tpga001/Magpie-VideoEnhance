## 1. 先明确三个共享层

| 共享层 | 当前实现 | 不是同一件事的部分 |
| --- | --- | --- |
| Frame Guidance | Renderer 持有服务；同一捕获帧生产一次；按目标尺寸缓存引导图 | 不是完整的、带多帧租约和消费者退役栅栏的资源池 |
| NGX Core | SR / NR / FG 共用 D3D12 device、Core 初始化和生命周期 | NR 与 FG 仍各自拥有队列、命令资源、颜色输入输出及互操作对象 |
| 前后端呈现环 | FG 正常运行时按倍率设置 2–4 个共享槽；事件、keyed mutex、代际检查保护复用 | 容量有界，但没有基于画面年龄淘汰过时插帧的策略 |

证据：[需求合并](../../../src/Magpie.Core/MotionVectorRequest.h#L68)、[帧服务](../../../src/Magpie.Core/FrameGuidanceService.cpp#L512)、[共享 Core](../../../src/Magpie.Core/NgxD3D12Core.h#L12)、[呈现环](../../../src/Magpie.Core/Renderer.cpp#L2514)。`DirectXHelper::CreateSharedTexture2D` 每次调用实际创建纹理并验证 NT handle，并非纹理池查找；稳定运行的复用由持有者和缓存完成。

## 2. 实际数据流

```text
新捕获帧：frameId + captureSequence + resourceGeneration + timestamp
  │
  ├─ 原始颜色 → NVOF 输入双缓冲 → nvOFExecute → 稠密运动 + confidence
  │                   HDR 时先做提供器自己的颜色转换
  │   Zero 引导资源 ───────────────────┐
  │                                   ↓
  │                         FrameGuidanceService
  │                         同帧缓存 / 目标尺寸适配缓存
  │                             │                 │
  │                             ↓                 ↓ 原捕获尺寸
  └─ 效果链颜色 → DLSSNR         │                 DLSS FG
                  ↑ 同帧、NR 效果输入尺寸引导       ↑ 最终效果链颜色
                  │                               │
           可选 SDR 输入降分辨率                   │
           + NR 专用引导降采样                     │
                  ↓                               │
           D3D11 → sharedInput → D3D12 NR           │
                  ↓                               │
           D3D11 输出 / 残差合成 → 后续效果 ────────┘
                                                  ↓
                              D3D11 → sharedInput → D3D12 FG
                              按 index=1..倍率-1 执行 Evaluate
                              每帧读禁用标志 → 发布生成帧
                              最后发布当前真实效果帧
                                                  ↓
                              共享呈现环 → 前端 FIFO → 时钟 + 容量门
                              前端底图 → 工具栏/光标 → Present
```

FG 不在效果列表原位置执行：它消费最终效果链颜色。NR 消费它在效果链位置上的颜色；光流来自原始捕获帧。尺寸适配只改变引导图分辨率和位移单位，不重新估算 NR 风格变化后的运动。

### 2.1 光流生产与消费

- `CollectFrameGuidanceRequirements()` 最终调用 `Resolved()`。当前会话优先 NVOF，并取实际请求中的最高档位；多个消费者不会各自重复启动同档光流。显式 None 的消费者继续使用 Zero 引导。[需求收集](../../../src/Magpie.Core/Renderer.cpp#L81)、[消费解析](../../../src/Magpie.Core/FrameGuidanceService.cpp#L572)
- `BeginFrame()` 按捕获 frameId 去重，普通重绘不会重做 NVOF；提供器持有两张颜色输入纹理。[帧去重](../../../src/Magpie.Core/FrameGuidanceService.cpp#L522)、[NVOF 输入](../../../src/Magpie.Core/NvidiaOpticalFlowProvider.cpp#L749)
- NVOF 初始化优先申请双向预测和 cost，再按能力降级；`Densify` 的反向运动/cost 用来计算 confidence，输出运动来自正向场。[初始化](../../../src/Magpie.Core/NvidiaOpticalFlowProvider.cpp#L579)、[稠密化](../../../src/Magpie.Core/NvidiaOpticalFlowProvider.cpp#L66)
- FG 只向 NGX 绑定颜色、motion、depth、输出和禁用标志，未绑定 confidence。NR 原生尺寸 Evaluate 也没有 confidence 输入；**NR 专用降采样会用 confidence 给 motion 加权**，置信度诊断效果也会读取它。[FG 参数](../../../src/Magpie.Core/DLSSFrameGenerator.cpp#L714)、[NR 参数](../../../src/Magpie.Core/DLSSNRFilter.cpp#L1414)、[NR 降采样](../../../src/Magpie.Core/DLSSNRFilter.cpp#L229)、[诊断消费](../../../src/Magpie.Core/FrameGuidanceDiagnostics.cpp#L126)
- 因而，FG-only / 关闭输入分辨率调整的 NR 有按需减少 confidence、反向场和 cost 的机会；不能全局取消它们，也不能假设改为单向请求后驱动输出逐位相同。启用调整但比例为 100% 的 NR，目前仍执行读取 confidence 的专用引导 pass，要与同尺寸快速路径一起处理。
- 应用 NVOF 的结果通过 `pMVecs` 交给 FG，并非把它注入 DLL 内部光流模块。应用侧共享不能被算作已经消除了 SDK 内部的估算成本；DLL 内部成本只能另行测量。

### 2.2 尺寸适配缓存

- 源尺寸与目标尺寸相同，服务直接返回共享视图。不同尺寸时，每个 `(request, extent)` 缓存 adapted/zero 两套 motion、depth、confidence，并按 frameId 缓存适配结果。[适配缓存](../../../src/Magpie.Core/FrameGuidanceService.cpp#L127)
- 通用适配使用双线性插值；NR 的缩小输入使用覆盖面积与 confidence 加权，并按目标/源尺寸缩放位移。两者不是可以任意互换的核。
- 例如“先超分，再 NR 缩小输入”，可能出现“捕获尺寸 → 效果输入尺寸 → NR 实际计算尺寸”两次引导采样，NR 另持专用 reduced 引导资源。可以研究共享等价转换，但直接改成一步采样可能改变结果；只有确实存在相同转换的消费者时，集中缓存才有复用收益。
- 即使调整比例为 100%，只要 SDR 的输入分辨率调整开关开启，NR 仍走 `PrepareReducedGuidance`。这部分存在同尺寸快速路径机会；残差控制仍须执行，不能连同残差功能一起跳过。[NR Draw](../../../src/Magpie.Core/DLSSNRFilter.cpp#L2243)、[残差约定](../../../src/Magpie.Core/DLSSNRFilter.cpp#L1663)
- 缓存当前以全部通道为单位分配。可研究按尺寸共享恒定引导、按实际通道分配、历史重置只失效内容而保留兼容分配。Zero 内容、格式、HDR 路径合同均保持原语义。

### 2.3 D3D11 / D3D12 互操作与 NR

- `FrameGuidanceD3D12Interop::Update()` 只在纹理身份变化时重开共享资源；稳定指针命中时直接返回。**不存在每帧都 OpenSharedHandle 的问题。** 纹理切换时会等待旧消费者，当前等待没有超时；只缓存当前一组映射。[互操作实现](../../../src/Magpie.Core/FrameGuidanceD3D12Interop.cpp#L16)
- NR 已有 **4 个命令槽**和延迟采集的 Evaluate GPU timestamp。CPU 主要在复用未完成命令槽时等待；帧尾的 D3D11 `Wait` 是 GPU 队列依赖，不能写成“NR 每帧都 CPU 等 Evaluate”。[命令槽](../../../src/Magpie.Core/DLSSNRFilter.cpp#L577)、[Draw](../../../src/Magpie.Core/DLSSNRFilter.cpp#L2211)
- 但各帧仍复用同一颜色输入输出，且 NR → D3D11 合成/后续效果 → FG 是有依赖的串行链。命令槽数量不代表颜色纹理也有四份，更不代表可以并发处理四个时间帧。
- NR 普通路径包含输入复制/格式转换、D3D11 Signal+Flush、D3D12 Wait/Evaluate/Signal、D3D11 GPU Wait、输出复制。缩小输入时还包括两次颜色降采样、专用引导降采样、残差准备、可选水平上采样、垂直合成及最后一次复制。[输入处理](../../../src/Magpie.Core/DLSSNRFilter.cpp#L1462)、[残差合成](../../../src/Magpie.Core/DLSSNRFilter.cpp#L1663)
- 候选优化是让兼容输出直接写目标 UAV，或在相邻原生后端间传递可共享颜色和完成栅栏。必须核对格式、HDR 白点/颜色域、尺寸、资源状态、纹理寿命和后续效果的访问方式；不能把所有跨 API 往返直接删除。
- 已有“相同 frameId + 参数修订 + 上游输入修订”去重及只重新合成残差的分支，应保留。FP16 HDR 路径目前不启用缩小输入/残差重建，这次不扩大其功能范围。[去重](../../../src/Magpie.Core/DLSSNRFilter.cpp#L2168)、[HDR 分支](../../../src/Magpie.Core/DLSSNRFilter.cpp#L1908)
- 当前 signed-snippet 兼容层使用单 owner，第二个 NR 实例可能在初始化时被拒绝。此次不以“多个同时运行的 NR 能省重复计算”作为已存在的收益，也不顺带扩展多 NR 实例支持。[owner 检查](../../../src/Magpie.Core/DLSSNRFilter.cpp#L852)

### 2.4 FG 的主要等待与复制

1. 每个真实输入先复制到 FG 的共享输入并 Flush。
2. 每个插帧使用同一 allocator、command list 和输出纹理执行 Evaluate。
3. 每个插帧复制 4 字节禁用标志到 readback，CPU 等 output fence，再读取首字节。该标志参与“发布还是跳过”的决定。[生成循环](../../../src/Magpie.Core/DLSSFrameGenerator.cpp#L663)
4. 回调 `_PublishBackendTexture()` 再复制到呈现槽，Signal+Flush 后 CPU 等复制完成，才投递前端消息。此等待也保护 FG 共享输出不被下一个 Evaluate 提前覆盖。[发布](../../../src/Magpie.Core/Renderer.cpp#L3544)
5. 前端依次复制共享槽 → 本地底图 → 呈现目标；提交成功后还复制一份稳定底图供独立 UI 重绘使用。[前端复制](../../../src/Magpie.Core/Renderer.cpp#L731)、[呈现目标](../../../src/Magpie.Core/Renderer.cpp#L819)、[稳定底图](../../../src/Magpie.Core/Renderer.cpp#L1003)

因此优先研究 **FG 命令/输出/标志槽 + 异步完成发布**，随后优化发布复制和最后使用者的栅栏。不是把两个 CPU 等待直接删除：单输出覆盖、命令 allocator 提前 Reset、禁用标志未就绪都会造成错误。第一张完成且有效的生成帧应能先发布，不能为了批处理等待整组 MFG 全部完成。

### 3.2 差距、优化点和适用边界

| 项目 | 当前状态 | r2 结论 |
| --- | --- | --- |
| 均匀间隔 | `FramePresentationClock` 迟到不超过一个周期时沿用旧 deadline，允许下一帧迅速追赶 | 增加最小间隔与有界相位修正，验证迟到、刷新率变化、插帧被禁用场景 |
| 时间来源 | `CaptureFrameCadence` 使用 `_BackendRender` 接受帧时的 `steady_clock`，仅减去 ring wait；已有捕获 timestamp 未用于这个估计 | 比较捕获时间与处理/投递时间，选择有效来源并保留失效回退；避免把下游开销误当源帧节奏 |
| 截止时间唤醒 | FG 的 Retry 不设置 `_frontendPacingDeadline`，主循环按短轮询/容量事件再试 | 共用能被输入和停止事件唤醒的 deadline 调度，分别统计等待 deadline 与等待容量 |
| 队列年龄 | 正常 FIFO 不按迟到程度淘汰插帧，没有每个 MFG 子帧的目标时间与年龄预算 | 容量有界之外再约束延迟；淘汰过时生成帧并保留有效真实帧，不能乱跳 NGX Evaluate 索引 |
| 帧身份 | 记录捕获 ID、序列、资源代际及 generated 布尔值；没有贯通的 `interpolationIndex / presentId` | 给帧对、插帧子索引、真实帧和实际呈现建立可追踪关系；用于排序测试、延迟测量和 Reflex |
| Reflex Low Latency | `src` 未检出 Streamline Reflex、NVAPI Sleep/SetSleepMode/SetLatencyMarker/GetLatency 调用 | 确认未实现；先完成多设备/异步呈现标记方案和原型验证，不能用 Sleep(1) 或 MaximumFrameLatency 替代 |
| 异步呈现标记 | 未接入 NVAPI 的异步帧标记/带外队列跟踪 | 若保留直接 NGX，核对这些公开接口如何映射 D3D12 FG 队列和 D3D11 前端呈现；不能把插帧伪造为新的源应用模拟帧 |
| 硬件节奏、VSync | 当前 DXGI 路线 `Present(0, flags)`；没有 Streamline 的呈现代理和对应硬件节奏集成 | Streamline Guide §22 的 VSync 能力检查、IFLIP 前提属于候选路线；不能直接给现有 D3D11 Present 套用 D3D12 Streamline 保证 |
| 显示端指标 | 部分计数是排队/成功提交次数；没有实际 scanout 证据 | 区分 captured/evaluated/queued/submitted/displayed。采用 FrameView 的显示变化间隔等外部指标核对，不能只报“倍率 × 基础 FPS” |

Reflex 是明确缺口，但 Magpie 只能控制自己进程的捕获后处理/呈现队列。无法从捕获帧恢复源游戏的 input/simulation/render 时间，也不能消除源游戏已经产生的排队延迟。这是根据 Magpie 架构和 Reflex 标记要求得到的适用范围判断，原型须以“捕获到显示的附加延迟”和 Magpie 自身交互延迟分别验收。

Streamline 要求其 DLSS-G 配合 `sl.reflex`；普通 NVAPI Reflex 不能替代 **Streamline 内部** 的标记联系。保留直接 NGX 时可以研究原生 NVAPI 路线；转用 Streamline 时则需要完整接入它的 Reflex/PCL。两条路线不混称。NVAPI 标为 Reserved 的低延迟 queue hint 不列为可直接使用的优化接口。

### 3.3 已验证的时钟边界

直接 include 当前 `FramePresentationTiming.h` 编译纯 C++ 控制台探针，不创建窗口或 GPU：周期固定 10 ms，上一 deadline 为 10 ms，模拟提交在该 deadline 后迟到。

| 迟到 | 下一 deadline 距刚完成提交的间隔 |
| --- | --- |
| 0 ms | 10 ms |
| 5 ms | 5 ms |
| 9 ms | 1 ms |
| 10 ms | 0 ms |
| 10.001 ms | 10 ms |

证明的是**应用时钟允许短间隔追赶，且一个周期边界处策略不连续**。不证明显示器一定发生同等间隔；DXGI 容量门、DWM 与驱动仍会影响显示。后续用可控时间序列测试修正调度，再做显示端验证。

### 3.4 在异步优化前处理的生命周期问题

- 发布复制 `_fenceEvent.wait()`、NR 命令槽/Drain 使用的 `WaitForFence()`、互操作换资源 `_WaitForConsumer()` 存在无超时等待。FG 自己的 fence 有 3 秒等待；这些等待的保护范围不同，不能只修一个。[发布等待](../../../src/Magpie.Core/Renderer.cpp#L3544)、[NR 等待](../../../src/Magpie.Core/DLSSNRFilter.cpp#L951)、[互操作等待](../../../src/Magpie.Core/FrameGuidanceD3D12Interop.cpp#L16)
- 资源失效需要显式区分 Retry 和 Drop。当前 `_UpdateFrontendBase` 检测旧捕获序列后返回 false，上层将 false 统一视为 Retry；还会推进访问 key，需测试下一次是否错误复用旧底图。这里已找到状态转换风险，**未进行真实窗口复现**。[过期分支](../../../src/Magpie.Core/Renderer.cpp#L708)、[FIFO 重试](../../../src/Magpie.Core/Renderer.cpp#L1321)
- `_DisableDLSSFrameGenerationForSession()` 清理 FG 和间隔，但未在该函数统一更新 `_hasFrameGeneration`、已排队任务、呈现环模式等。应以完整状态转换测试确定停用后的收尾，避免优化后遗留 FG 调度状态。[停用](../../../src/Magpie.Core/Renderer.cpp#L2387)
- NGX 参数调用已有异常保护、NR/FG 有 Drain。增加异步资源后应按最后消费者完成值退役；超时不能被当成资源已经安全释放。

## 4. 优先级判断

优先建立能区分等待与计算的基线，修正时钟及资源退役边界；随后做按需 confidence、同尺寸/同转换引导复用、FG 输出槽和发布交接。Reflex 并列为低延迟原型方向，完整 Streamline 迁移只做方案比较，不将大规模呈现重写作为 r2 默认前提。

保留已有同帧去重、共享提供器、NR 命令环、NeverProvided 优化和全屏前置保护。判断优化是否成功，应同时看 p95/p99、画面年龄、真实帧交付、显存和停止响应，不以 CPU 提交函数变快单独判定。

本机调查证据保存在工作区 `.tools/067-r2-research/`：固定版本文档副本、PDF 摘录与关键页图、`timing-probe.cpp`、运行脚本及结果。第三方文档副本和可执行探针不进入源码提交。
