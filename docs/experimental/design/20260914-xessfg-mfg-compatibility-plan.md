# XeSS FG 多帧兼容模式接入方案

日期：2026-09-14。状态：用户已确认并授权实施；代码、独立回归及首轮 Release 构建已完成，最终部署审计另见 068 local 的部署记录。

本次所指研究为任务“查找 xessmfg 和 dlssmfg 研究”（`01a09d98-9637-7183-b439-3db36b1dff26`）中的 XeSS MFG 社区解锁。Magpie 基线为 `40dbe7b79cff154fc50241b6082951b040299dc2`；社区源码固定到 Coldwood1026/OptiScaler 的 `70676c5f037c8c26f1ec355b250a72303cd268da`。

## 1. 建议结论

按用户本轮要求，将现有 x2 与 MFG 两个效果器合并为唯一的 XeSSFG。首期目标是在支持 XeSS FG 基础运行条件的非 Intel 显卡上运行 3×/4×。实现范围包括效果器合并、旧配置自动迁移、能力限制处理、指定版本运行库的内存补丁、输入计时适配、生成帧节奏修复及验证。

首期倍率保留 2×～4×。新建 XeSSFG 默认使用 2×、AMD 光流、质量；旧 x2/MFG 迁移时倍率设为 2×，光流方法及对应质量沿用用户此前的选择，不统一重置为 AMD 质量。多帧兼容能力默认自动启用，不新增要求用户选择的兼容模式参数；2×及 Intel 原生支持路径使用 SDK 原始行为，非 Intel 的 3×/4×自动启用经过核验的补丁及配套节奏修复。倍率变化通过重建缩放会话生效。后续用户修改的新效果器参数正常保存，不在每次启动时重置。

本方案具备代码与二进制布局上的可行性证据；尚无本机运行解锁后的 XeSS MFG、画质、显示帧间隔或 GPU 性能验证。

Magpie 是外部捕获工具：输入为捕获颜色、平面深度、单位相机矩阵，以及可选外部光流。现有 MFG 效果器只开放无光流/AMDOF，独立 x2 还支持 NVOF。新建效果器默认输入为 AMDOF 质量；迁移保留旧效果器的光流方法及质量，包括旧 x2 的 NVOF。3×/4×首期沿用无光流/AMDOF 的支持范围，避免未经验证地扩大 NVOF 多帧支持；用户切换到不支持的倍率与光流组合时明确提示，不静默改写其光流配置。

Magpie 的独立 UI 图层可以保护自身叠加界面，但无法自动拆出捕获画面中游戏自带的 HUD。因此，社区游戏内接入的画质结果不能直接迁移到 Magpie。

## 5. 候选方案比较

| 方案 | 预期结果 | 判断 |
| --- | --- | --- |
| 仅移除 Magpie 的 Intel 判断 | 运行库仍可能报告仅支持插入一帧，或内部回退 | 不完整 |
| 移除判断并接入五处解锁 | 有机会真正启用 3×/4×，但生成帧节奏仍待处理 | 作为内部对照构建 |
| 解锁＋输入计时适配＋逐生成帧节奏修复 | 同时验证生成数量和运动平稳度 | 首期推荐交付目标 |
| 同时扩大到 5×～8× | 增加计算、显存和显示节奏验证范围 | 留待 3×/4×通过后单独推进 |

这里的 4×指一个真实输入帧加三个生成帧。官方 SDK 已有设置插帧数量和查询最大插帧数量的接口；官方 XeSS 3 的 MFG 支持说明面向 Arc，社区路径需要单独标识。[Intel 接口](https://raw.githubusercontent.com/intel/xess/main/inc/xess_fg/xefg_swapchain.h)、[官方发布说明](https://github.com/intel/xess/releases/tag/v3.0.0)

## 6. 推荐实现设计

### 6.1 唯一效果器、默认值和自动兼容

- 统一内部 ID 为 `XeSSFG\\XeSS_FrameGeneration`，界面只显示一个 XeSSFG。同步更新效果选择器、默认效果组、参数本地化、后端分类、光流请求、HDR 路由和帧率倍率计算；不再区分面向用户的 x2/MFG 两个效果器。
- 新建效果器默认参数为 `multiplier=2`、`opticalFlowMethod=1`（AMD）、`amdOpticalFlowMode=1`（质量）。旧 ID 迁移时仅将倍率初始化为 2，保留用户原有 `opticalFlowMethod`、`amdOpticalFlowMode`、`nvidiaOpticalFlowQuality` 等合法光流设置；原来选择“无”、AMD 性能/质量或 NVIDIA 的具体质量档位，迁移后仍为原选择。字段缺失时按旧效果器的有效默认语义补齐；非法值走明确的配置修复规则。后续在新 ID 上保存的用户调整保留。
- 兼容能力默认开启且自动判定，不新增用户必须操作的 `mfgCompatibility` 参数或开关。非 Intel 的 3×/4×自动尝试已验证的兼容实现；2×和 Intel 原生路径使用 SDK 原始行为。
- 版本不匹配或补丁初始化失败时，明确提示兼容模式不可用。请求 4×时不静默改成 2×，避免配置值与实际输出不一致。
- 不再把库上报的限制一律描述成“硬件最多支持”；区分原生能力、兼容模式支持情况和实际初始化失败。
- “解锁但不修节奏”等开关只用于开发诊断；正常用户通过倍率和光流参数使用统一效果器。

### 6.1.1 首次打开新版 068 的迁移规则

首次加载配置时，扫描所有效果组中的两个旧 ID，在原位置替换为新 ID，倍率初始化为 2×，光流估计配置继承被替换的旧效果器。保留效果组名称、配置文件对效果组的引用、其他效果器及其顺序、该效果器的通用缩放属性。

以独立的 XeSSFG 配置迁移版本记录完成状态，不只检查应用版本号是否为 0.6.8，保证已经使用旧 068 的用户也会执行迁移。迁移前使用现有不可变备份机制，迁移结果与标记一起原子保存；保存失败不能当作迁移完成。

启动加载与导入旧效果组共用旧 ID 转换逻辑。以后再次导入旧 x2/MFG 时仍转换并保留其光流选择，新 ID 已保存的合法参数不重复重置。如果同一个效果组中含有多个旧/新 XeSSFG，建议保留效果链中第一个的位置及光流配置，并合并掉其余重复 XeSSFG；不同效果组各自保留一个，不合并用户的效果组。

核对迁移顺序：现有 `ApplyOpticalFlowDefaultsMigration` 会把旧版光流默认值改为“无”，因此必须在此类破坏性归一化之前保留旧 XeSSFG 的合法光流选择，再转换为新 ID，并确保新 ID 不被该历史迁移覆盖。不能先清空旧光流选择再声称迁移保留了用户配置。`ScalingModesService` 对旧 MFG 的参数归一化也要配套改造，避免覆盖继承的设置或误删参数。

安装目录只分发新的正式效果文件。068 local 部署时清理两个已退役的官方旧文件并更新清单和 ZIP；旧配置兼容由加载/导入映射处理，不通过继续显示两个旧效果器实现。

### 6.2 补丁管理与会话生命周期

新增独立补丁管理模块，由 Presenter 初始化调用。针对当前已核验的 x64 DLL，采用文件哈希、PE 标识、全部原字节和模块边界联合校验；未登记版本不做猜测性补丁。

把解锁与所需节奏入口作为完整事务：先检查全部位置，再修改；保存每个位置的原值，写入回读并检查保护恢复、指令缓存刷新。失败时包含当前失败位置一起回滚并核验，不能把“尝试恢复”视作恢复成功。无法证明镜像完整时终止本次 XeFG 初始化。

补丁是模块级状态，不能简单挂在一个临时 Presenter 对象上。需要统一管理存活 XeFG 上下文，在没有活动调用和 SDK 工作线程使用这些入口时安装/撤销。会话停止时先停止提交、排空 GPU、释放交换链并销毁上下文，然后恢复原始入口；验证此后同进程切回 x2/原生模式不残留行为。

实现前核实供应库最终执行的 provider 身份。只读文件匹配结果不能替代运行时模块路径及执行入口检查；已有修改、未知 provider 或无法确认生命周期时，拒绝启用该兼容路径。

保留借鉴代码的来源、固定提交和许可证声明。运行发行包继续放原始运行库；本方案不生成打过补丁的磁盘 DLL。

### 6.3 输入计时与帧节奏

需要分别记录：源捕获帧间隔、Magpie 接收/提交间隔、XeLL 等待、Present 阻塞、额外节奏等待、实际交给 SDK 的 `frameRenderTime`。SDK 将该字段定义为当前帧渲染耗时；外部捕获无法直接得到游戏内部 CPU/GPU 渲染耗时，任何替代值必须标记为估计值。[字段定义](https://raw.githubusercontent.com/intel/xess/main/inc/xess_fg/xefg_swapchain.h)

将前端实际消费的帧元数据传给 XeSS Presenter，包括 frameId、captureSequence、resourceGeneration、timestamp100ns。不要从后台“最新帧”读取时间，否则可能与正在呈现的颜色/光流错配。即使关闭外部光流，输入帧身份与时间也应可用。

首选验证有效、单调的捕获时间差作为源节奏估计，同时记录接收时刻和队列积压；WGC 时间差不是游戏渲染耗时，漏帧时也不能假定它代表一个原始游戏帧周期。对没有有效捕获时间的来源，比较经过等待归因的提交间隔与社区估计法，选择不会形成自反馈的稳定回退。

不直接使用“整段 Present 时间全部扣除”或“捕获间隔全部扣除”的统一公式：游戏捕获与 Magpie 呈现可以并行，扣除不属于该时间区间的等待会低估周期。输入流间隔与 SDK 时间提示分开保存，通过对照记录决定估计规则。

节奏修复只对当前兼容上下文且实际多帧输出生效。每个输出批次内固定间隔，基准随新批次更新；预热、暂停、捕获重建、尺寸变化、倍率切换、输入倒退时清空旧估计。若已错过 deadline，不能连续快速补交来“追赶”旧时刻。

XeLL 负责现有低延迟和基础输入限制，容量对象负责队列容量；兼容节奏模块负责批次内部的生成帧间距，不再叠加另一套基础帧限速器。保留官方调度器负责的等待，避免同一帧重复等待。

社区代码中的全局时序变量需要按上下文管理，并审查 SDK 线程与前端线程之间的数据同步。hook 回调不得抛出异常或执行大量同步日志；统计通过有界记录异步汇总。

## 7. 验证和交付次序

1. 先实现唯一效果器与配置迁移，验证旧 x2、旧 MFG、自定义效果组、重复 XeSSFG、已经使用旧 068、保存失败重试、再次启动、导入旧配置以及新参数不重复重置；覆盖“无”、AMD 各质量档、旧 x2 的 NVIDIA 各质量档及缺失字段，验证迁移保留原光流选择；单独验证新建效果器的 AMD 质量默认值，防止历史迁移覆盖上述配置。随后实现能力决策、补丁事务和生命周期，增加未知 DLL、字节不匹配、写入失败、回滚失败、重复初始化及同进程倍率切换测试。
2. 建立原生 2×、仅解锁 3×/4×、解锁并修复节奏三组对照；最后两组均只对已匹配运行库执行。
3. 验证“不同真实输入帧数、SDK 实际生成/呈现数量、最终显示帧数”三个层面。不能把 `framesPresented` 或 Magpie 外层 Present 日志直接当作显示器已经均匀显示的证明。
4. 记录逐输出提交间隔，并结合 ETW/PresentMon 的可用显示事件核对实际显示间隔、丢帧和重复帧；若显示事件不可得，明确保留该验证缺口。未饱和显示条件下，检查预热后实际倍率及 P50/P95/P99 间隔，报告基础帧率是否随倍率异常下降。
5. 覆盖 30/45/60 FPS 输入、稳定与波动节奏、VRR 开关、超过显示刷新率、Zero MV/AMDOF、SDR/HDR、暂停/恢复/切换窗口/尺寸变化/反复启停。GPU 覆盖按实际可用硬件报告，不把单卡通过扩大为全厂商通过。
6. 检查快速横移、遮挡边缘、细线、游戏 HUD 和鼠标；同时比较 GPU 耗时与显存，区分生成帧画质问题和显示间隔问题。
7. 构建及必要检查通过后形成可试用版本；068 local 部署和 release ZIP 更新在用户确认本轮实施范围后进行。未完成显示/画质测试时以实验验证状态交付，不宣称兼容性或质量已经全面验证。

## 9. 本轮实现与实测记录

- 唯一效果器 `XeSSFG\\XeSS_FrameGeneration`；新建默认 2×、AMD、质量，旧配置迁移保留光流。`experimentalXeSSFGSettingsVersion=1` 与配置原子保存；旧 ID 转换先于历史光流默认迁移，导入复用同一转换函数。同组重复 XeSSFG 保留第一个。
- 模块租约覆盖原生和兼容上下文。哈希、PE、八处补丁原字节以及四处 native 函数入口原字节联合检查；八处作为事务安装，失败回滚包含当前写入位置。恢复检查页面保护和指令缓存；SDK 销毁失败、有活动 hook 或恢复失败会阻止本进程继续创建 XeFG 会话。
- 使用前端实际取出的元数据，独立于外部光流是否开启。记录捕获差、接收差、前端等待、提交差、XeLL、Present、额外节奏等待及输入估计。没有连续有效捕获时间时，仅从提交区间扣除上一轮同步 Present 内实际测得的额外 pacing 等待，不扣整段 Present。
- GPU 测试暴露了仅按 SDK ring 中位数修正 deadline 的正反馈。现在批次步长优先取独立捕获／归因提交周期，避免把自身等待反复加入周期；批次内保持步长，过期 deadline 向当前进度重定位。SDK 计数、provider 调用与显示事件分别解释，hook 内不格式化日志，512 条有界记录提供提交间隔分位数。

验证设备为 NVIDIA GeForce RTX 5070 Ti，驱动 `32.0.16.1692`。`Run-XeSSFGRuntimeSmoke.ps1` 使用 640×360 SDR 合成移动色块、平面深度及零运动向量，覆盖原生 2×、仅解锁 3×/4×对照、完整兼容 3×/4×和同进程反复恢复 2×。每轮 40 个输入，忽略前 5 个预热后，35 次提交均返回完整倍率：2×为 70 帧，3×为 105 帧，4×为 140 帧。完整兼容路径的 provider 和 scheduler hook 已实际执行；回到 2×后能力恢复为单插帧，全部上下文初始化、退出成功。

自动检查包括：`Run-XeSSFGCompatibilityTests.ps1`（旧 x2/MFG 的所有光流／质量组合、缺失／非法值、新建默认、重复条目、幂等；八个写入故障位置及回滚失败；时间倒退／换代／暂停／重复／漏帧；deadline 修正与防计时反馈；匹配 DLL 在独立进程中的反复安装／恢复）；`Run-ConfigMigrationTests.ps1`（真实配置保存与恢复机制、不可变备份和失败重试）；`Run-EffectPickerR1Tests.ps1`（157 项目录、真实 XAML 选择项及布局）；`Run-Beta3Tests.ps1`（显示名称和原参数迁移）。最终构建、文件及 ZIP 校验记录保存于工作区 `.tools/xess-mfg-impl/` 与 `release/v0.6.8-local/`。

## 10. 2026-09-14 捕获序号修复与真实链路验证

用户报告 2×正常、3×/4×不工作。14:57 的日志中兼容补丁、能力查询和初始化成功，但 3×为 720 次提交/720 帧，4×为 480 次提交/480 帧，输入估计恒为零。`FrameSourceBase::CaptureSequence` 仅在捕获中断时变化；`XeSSFGTiming` 错误使用 `sequence <= previous.sequence` 判重，并用 `sequence + 1` 判连续帧，导致每帧向 SDK 设置 resetHistory。原 GPU 合成测试固定 frameRenderTime 且仅首帧重置，未覆盖正式计时器；原单测也错误模拟了逐帧递增的会话序号。

修正后按会话变化判重置，按 frameId 连续性选择捕获间隔或归因提交间隔。保留资源换代、时间倒退、重复源帧和长暂停保护。新增 120 个同会话连续帧只重置一次的回归，并使 GPU 合成测试使用正式计时器，模拟捕获重启和资源换代。每轮 45 个计数样本均为完整倍率：90/135/180 帧，且可恢复原生 2×。注意 frameId 是 Magpie 接收的捕获帧身份，不能据此断言 WGC 上游从未丢帧。

显示名统一为 `XeSS_FrameGeneration`，与 `DLSS_FrameGeneration` 对齐；更新效果选择器目录、前端名称和覆盖层名称，保留内部 ID、光流配置及效果组名称。新增统一 SDK 输出计数日志，并在兼容日志中打印源帧、会话、资源代次和计时重置状态。

真实链路测试使用 `Run-XeSSFGCaptureSmoke.ps1` 和自动退出的动画窗口，运行独立的便携配置，不读写用户配置。RTX 5070 Ti、SDR、窗口模式、WGC＋AMD 质量光流，关闭 RTSS 后完成 2→3→4→2→DLSSNR＋4×：累计 SDK 帧数/提交数为 951/480、1066/360、1425/360、957/480、1413/360；包含启动及捕获中断历史重建产生的单帧。4×连续两个 120 次提交区间均输出 480 帧。DLSSNR 组合使用 50% 输入分辨率、单次 Multi Pass、低频时域重建。自动化验收按每个会话分别检查，不让另一段 4×的统计替代 DLSSNR＋4×场景。

另发现独立的 RTSS 环境问题：一次多轮切换在新交换链初始化中经过 RTSSHooks64 / nvapi64_impl / D3D12Core 触发控制流保护失败（0xc0000409，子码 0xa）。更换测试进程名称仍加载 RTSS 的全局配置，其 60 FPS 限制干扰多帧提交。用户退出 RTSS 后，原 Magpie.exe 名称的完整切换和组合测试通过。未修改 RTSS 用户设置，未把本轮修复宣传为已解决 RTSS 注入兼容性。

## 11. RTSS 兼容性后续定位

进一步读取转储确认：触发调用为 RTSS 注入的 `NvAPI_D3D_SetLatencyMarker`（API ID `0xD9984C05`），参数 frameID 为 `0x5254535300000935`，带 RTSS 签名。NVAPI 查询 D3D12 设备接口时出现内层访问异常，随后控制流保护终止进程。无效接口的具体来源尚待对照定位；不能单凭最终 CFG 错误将其归为缺少跳板注册。

原名 Magpie 的 RTSS 配置 `Limit=0`，开启 Reflex 标记注入；全局 60 FPS 属于换名测试的另一问题。原名开启 RTSS 的日志中 3×曾有 360 次提交／1078 张 SDK 输出，说明不能将“3×必然失败、2×天然安全”作为结论。

完整证据、按进程保留 OSD／协调 Reflex 注入与 XeLL 的方案、多帧调度加固及验收矩阵见 [XeSSFG 与 RTSS 兼容性方案](20260914-xessfg-rtss-compatibility-plan.md)。本轮仅研究和文档，没有改动运行时或部署包。

慢启动问题及正式期限修复另见 [启动 pacing 调查](20260914-xessfg-startup-pacing-investigation.md)。RTSS 重建期崩溃与可恢复的启动低帧率分开处理。
