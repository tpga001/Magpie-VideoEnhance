# XeSS FG 3×／4×慢启动：周期估计与调度等待的反馈

日期：2026-09-14。调查基线：068 `3ac545454c33`。第 1～6 节记录“画面已经出现，但帧率几秒至几十秒后才升高”的调查与单变量实验；正式修复见第 7 节。

## 1. 结论和原方案修订

**本机已复现并通过单变量对照定位：多帧 timestamp 调度在判断迟到后追加完整输出间隔，与受背压影响的捕获周期估计形成反馈，导致启动阶段越来越慢，然后才恢复。它不是 SDK 必须等待固定秒数才能开始生成多帧。**

RTSS 保持运行，所有六次测试的首帧诊断都记录 `rtss=true`。仅跳过 `TsDetour` 的迟到延期分支，4×前 120 次提交从 10.176／11.917 秒缩短到 2.980／3.158 秒，接近 2×的 2.947 秒。两次干预均保留其余补丁、XeLL、捕获、光流、RTSS 和倍率设置。

此前崩溃转储中 RTSS 注入 Reflex 标记、NVAPI 查询设备时异常的证据仍成立；那是独立的初始化／重建期问题。不能把本轮可自行恢复的低帧率解释为同一次崩溃机制，也不能从本轮未崩溃推断已解决所有 RTSS 兼容问题。

**后续优先修正多帧调度和输入周期估计；不再把关闭 RTSS 标记注入作为解决慢启动的必要前提。**

## 3. 隔离对照数据

设备：NVIDIA RTX 5070 Ti。原名 `Magpie.exe`，WGC，AMD Quality 光流，SDR，全屏缩放，目标基础上限 60 FPS；动画源窗口仍采用现有 GDI fixture。该源实际稳态约 40 次提交／秒，因此 120 次提交约需 3 秒，不能把它当作严格的 60 Hz 游戏源。

RTSS 专用配置保持 `Limit=0`、`ReflexSleep=0`、`ReflexSetLatencyMarker=1`、`UseDetours=1`、`InjectionDelay=15000`。磁盘值不替代生效状态查询，但每次首帧都实际检测到 RTSS 模块，故本轮的 10 秒慢启动不能解释为“等待 15 秒才开始加载 RTSS”。

## 4. 具体反馈是如何形成的

### 4.1 慢的启动样本被当成稳定源帧周期

第一次 4×诊断中：

| 源帧编号 | 送给调度的估计周期 | 本次 Present | 调度相关额外等待 |
|---|---:|---:|---:|
| 2 | 46.497 ms | 8.494 ms | 0 |
| 3 | 46.497 ms | 52.543 ms | 34.873 ms |
| 10 | 46.636 ms | 55.502 ms | 35.610 ms |
| 30 | 106.664 ms | 131.194 ms | 80.198 ms |
| 40 | 153.330 ms | 176.968 ms | 107.732 ms |
| 50 | 186.660 ms | 137.356 ms | 93.217 ms |
| 120 | 26.661 ms | 6.609 ms | 0 |

所有这些阶段都已在生成 4×。低帧率来自一轮输出占用越来越长的时间。

`XeSSFGTiming::Submit` 在 `current.frameId == previous.frameId + 1` 时把捕获时间戳差标为可信的源周期，并用 9 样本中位数稳定它。但 `Renderer::_BackendRender` 的帧号只按“本次接收并处理的新帧”递增；`GraphicsCaptureFrameSource::_Update` 会把池内多个帧取出，仅处理最后一个。**帧号连续不代表 WGC 没跳帧。**

所以背压导致的 60／100／180 ms 捕获间隔仍会被当作一个源帧周期，而不是“这期间没来得及接收中间帧”。独立捕获时间戳免疫的是读取时刻误差，不会自动免疫消费者背压造成的采样稀疏。

### 4.2 迟到分支把已经发生的等待继续追加到未来

`XeSSFGPacing.h::TsDetour` 的关键行为：

```cpp
// first deadline is in the SDK time domain; wall anchor is sampled here
deadlineAnchorNs = firstDeadline;
deadlineAnchorQpc = wallNow;
// later output in the burst
if (elapsed > nextDeadline - deadlineAnchorNs)
    nextDeadline = deadlineAnchorNs + elapsed + burstStep;
```

第一个锚点保存的是第一张输出的 deadline，不能直接视为采样 QPC 时刻对应的 SDK“现在”。后续等待已经消耗时隙时，迟到分支仍把期限延为“已经过去的时间＋完整输出步长”。这会向本轮后续输出追加等待。

逐帧诊断中该分支计数在启动时快速递增，周期估计和等待量一同增长。关闭这一个分支、继续使用首次 deadline 加固定步长，便消除了两次 4×测试中的大幅增长。这是本轮最强的因果干预证据。

形成循环：**启动间隔偏大 → 多帧调度等待增加 → WGC 接收更稀疏 → 估计周期继续增大 → 后续调度更慢。**

`extraWaitMs` 仍包含 native scheduler 调用耗时；它不能全部归为手写 Sleep。即便只移除时间延期，scheduler 的等待也会因此减少。

### 4.3 为什么 4×更严重，以及为什么会自行恢复

- 2×使用原生路径，不进入这些多帧兼容调度修改。
- 3×每个完整 burst 在补丁路径中增加一次中间输出调度，4×增加两次；SDK 自身还会访问 timestamp 路径。更高倍率增加了错误期限调整影响同一 burst 的机会。
- 中位数按“样本数量”更新；一旦每个样本耗时变长，等待同样数量的新样本就会从几百毫秒变成数秒。
- native 调度状态、实际到帧相位、历史窗口和捕获重启会改变迟到判定。在首次复现中，延期计数增长放缓后周期逐渐回落；用户日志中捕获重启也与恢复相邻。

尚未把 SDK 内部每个状态切换与恢复时刻一一对应，因此不宣称找到了唯一的自动恢复触发器。**可变的反馈收敛时间已经能解释倍率相关的慢启动；没有证据要求固定 10／15／30 秒“预热”。**

## 5. 应采用的修改路线

1. **先修正 burst 的期限计算。** 保持一致的 SDK 时间域和固定锚点；时隙已消耗时不再逐张追加完整间隔。实验中的“跳过分支”用于定位，正式实现还要处理极端迟到、避免一次性拥挤提交，并在下一 burst 重新定相。
2. **修正输入周期的可信度。** 区分源生产节奏、WGC 丢帧／取最后一帧、后端等待和最终接收节奏；不能用喜鹊自己的连续帧号证明未跳帧。启动／重建后的少量异常样本不能直接驱动大幅增长。也不能把所有游戏硬编码成 60 FPS，或把整个 Present 时间一律减掉。
3. **补充启动与扰动回归。** 固定 30／40／60／低帧率源、冷启动、首帧慢、临时 GPU 阻塞、暂停恢复、3×／4×反复切换；再测 RTSS 退出／OSD／不同限帧组合。最终用显示事件核对倍率、平滑度和延迟。
4. **RTSS 标记崩溃单独处理。** 保留原转储证据与重建测试，不因为这次慢启动就自动改写 RTSS 配置；也不承诺本轮方案已经解决重建期崩溃。

XeSS FG 当前已由 XeLL 接管内部帧同步；把喜鹊界面的 Reflex 改成 Async 不会改变这条多帧调度路径。Intel 也要求避免多个额外限帧器影响 XeLL 的计时，但这项要求不能替代本轮对具体代码缺陷的定位。[XeLL 指南](https://github.com/intel/xess/blob/main/doc/xell_developer_guide_english.md#requirements)

## 7. 正式修复（2026-09-14）

### 7.1 固定 burst 期限，消除重复延期

- `TsDetour` 完全使用 SDK 时间域：第一张观测输出取 native deadline 并还原倍率步长，后续按输出索引差推进固定期限。移除将“未来 deadline”当作“当前 QPC 时刻”的锚点及迟到追加完整间隔的逻辑。
- 每个新 burst、倍率变化、会话／资源重置都重新取锚点。跳过某个索引仍落在原定时隙；首次观测到的不是索引 1 时也可以正确初始化。
- fallback `PaceFrame` 同样不再把过期期限改成 `now + interval`。GPU 或 Present 已占用的时隙不重复补等。
- 过期时隙交由 native scheduler／Present 消费；每轮只有最多 3 个生成帧时隙可追赶，不携带跨 burst 的时间债务。这里采用**有界追赶**，没有给每张迟到帧再加人为最小等待，也不修改 SDK 的丢帧策略。短时拥挤输出仍可能存在，需要显示事件验证；避免拥挤不能靠恢复本次证实有害的逐帧延期。

### 7.2 启动估计与可信度边界

- 启动只有两个有效样本时使用较短值；三个及以上仍用最近 9 个样本的中位数。首个慢样本因此不会因偶数窗口取上中位数而继续主导第二次估计。第一个样本仍可参与调度，没有捏造一个固定基础 FPS。
- 保留已知跳过提交时的 fallback、捕获会话／资源换代／长暂停／倒退重置。测试覆盖 16／25／33／100／250 ms 周期、400 ms 首次慢样本、持续切换到 200 ms，以及暂停后恢复。
- 明确 `captured` 只表示采用接收帧的捕获时间戳间隔；连续 frame ID 不能证明 WGC 没丢中间帧。当前未新增 WGC 生产帧序号，也没有假装消除了所有背压采样误差。主要修复是切断错误调度造成的正反馈；完整源生产节奏估计仍是后续独立工作。
- 保留 `MAGPIE_XESS_STARTUP_TRACE=1` 首 240 帧诊断，默认日志仍每 120 帧输出。诊断中的期限偏移是相对 native deadline 的差值，已删除旧算法含义不成立的迟到计数。

- 单元回归及固定 DLL 的补丁安装／回滚检查通过；新增超时、索引跳跃、倍率变化、fallback 和启动／低帧率估计用例。
