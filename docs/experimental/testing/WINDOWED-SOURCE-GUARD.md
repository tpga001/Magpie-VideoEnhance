# 窗口模式的全屏源保护

窗口模式启动时，`SrcTracker::Set` 在应用裁剪前读取源窗口的可见边界、客户区和所属显示器的完整边界。源窗口覆盖整台显示器时，立即返回 `BannedInWindowedMode`（MP-009）。`ScalingWindow::_StartImpl` 在创建缩放窗口和初始化 Renderer 之前处理这一返回值，因此该输入不会进入捕获或厂商 GPU 效果。

判断不依赖最大化标志或窗口样式；使用显示器完整边界而不是工作区、缩放输出位置或裁剪后的大小。显示器边界读取失败时返回显示布局错误。原有最大化检查继续生效，允许全屏效果的设置也不会绕过窗口模式保护。

普通窗口的窗口模式使用这项源边界检查，移除了后续与输出矩形比较的旧判断。0.6.7-local 同时把全屏效果模式的限制前移到这里；已开启“允许缩放最大化窗口”时，全屏效果模式仍可继续。完整启动前检查见 [SCALING-PREFLIGHT.md](SCALING-PREFLIGHT.md)。

简体中文提示为：

> 源应用已最大化或处于全屏状态。请先在源应用中切换为窗口化，并将窗口还原到小于屏幕的尺寸，再启动窗口模式效果。

繁体中文和英文使用相同操作引导。

## 验证

`scripts/tests/test_windowed_source_preflight.py` 提取生产代码中的新检查和原最大化检查，生成不创建窗口、不初始化 GPU 的 C++ 测试。它验证：

- 2560×1440 全屏源和未设置最大化标志的无边框源被提前拦截。
- 可见边界与客户区分别覆盖显示器时都能识别，普通窗口和工作区大小的非最大化窗口仍可通过。
- 不同比例的物理像素布局、副屏负坐标、竖屏和跨屏源。
- 显示器信息读取失败时提前退出；全屏效果模式在允许最大化缩放时通过，未允许时提前拦截。
- 静态检查生产调用顺序：源检查与错误返回先于 `CreateWindowEx`、Renderer 初始化；新判断位于裁剪前。

在 Visual Studio x64 开发命令行中，可先用 Python 脚本生成测试，再使用 `/std:c++20 /EHsc /I src/Magpie.Core/include` 编译生成的 `windowed_source_preflight.cpp`。

这些是 CPU 回归和物理坐标用例，不能代替真实多显示器/DPI、游戏和 GPU 画面的验收。本项修改只提供入口保护，不代表已经查明或修复 0.6.6 → 0.6.7 的 GPU 黑屏回归根因。
