# 浏览器原始视频帧增强 0.2.0

## 本次改进

输入改为浏览器解码后的原始视频帧。1080P 视频即使在网页中显示成 3747×1979，也仍以 1920×1080 进入超分，避免先被浏览器拉伸，再对拉伸结果处理。

- 4K 屏幕上，1080P 输入可在内部处理到 3840×2160，再显示到网页原有的视频区域。网页、书签栏和窗口尺寸不随之放大。
- 处理尺寸继续跟随视频所在显示器。1080P 源在 1080P 屏幕上不额外放大到 4K。
- 支持窗口和播放器区域改变、暂停恢复；退出 Magpie 后不会由被动视频上报重新启动。
- 识别到的 B 站网页字幕、控件和弹幕区域保留浏览器原画。烧录在视频中的文字仍属于视频内容，不能保证补帧后完全没有形变。
- 不支持读取的跨域、受保护、HDR 或特殊变换视频会显示原因并退回浏览器原画，不把网页截图冒充原始帧。

## 使用

在 `chrome://extensions` 或 `edge://extensions` 刷新「Magpie 浏览器视频增强」，确认版本为 **0.2.0**。随后刷新视频页面，将增强开关关闭再开启。

正常接入 1080P 视频后，扩展应显示 **原始帧增强 · 1920×1080 输入**。这表示原始帧已被本机主机接收且增强请求已送达；最终渲染效果仍需结合画面和 Magpie 日志判断。

## 验证记录

2026-09-27，在隔离的真实 Edge 扩展配置中，使用确定为 1920×1080、30fps 的 SDR 测试视频验证。仅替换原生主机名称指向候选运行时，没有模拟扩展 API 或帧传输。

| 项目 | 结果 |
| --- | --- |
| 原始视频输入 | 日志确认 `BrowserDecodedFrame`，1920×1080 |
| VSR | `1920x1080 -> 3840x2160`，quality=2，实际 Draw 成功 |
| 连续处理 | 超过 300 原始帧，XeSSFG 输出正常 |
| 显示区域 | 1617×909；窗口缩小时变为 1242×698，输入仍为 1920×1080 |
| 网页字幕避让 | 原生窗口区域检查确认字幕中心不在增强窗口区域内 |
| 暂停/恢复 | 暂停撤掉增强覆盖层，恢复后 VSR 重新工作 |
| 手动退出 | 扩展开关转为关闭，观察期间没有重新启动 Magpie |
| 自动检查 | 16 项 JavaScript 回归测试、C# 帧协议校验、显示器原生尺寸策略测试通过 |

日志中第 300 到第 600 帧间隔约 10.65 秒，约 **28.2 原始帧/秒**。这是该次短时测试的处理速率。XeSSFG 的生成计数不等于屏幕实际显示帧率，不能据此宣称稳定 60fps。

桌面截图被前景中的其他窗口遮挡，未作为画质验收依据。本次未确认用户日常 Chrome 中当前 B 站视频的最终画质，也没有证明文本水波纹完全消失。

证据位于工作区 `output/playwright/browser-decoded/extension-result.json` 和 `extension-runtime.log`。测试日志会轮换，验证脚本同时读取当前与上一份日志，并使用全新的隔离配置避免浏览器缓存干扰。

## 实现边界

`VideoFrame.copyTo()` 读取原始 SDR 像素，优先使用 NV12/I420，其他受支持输入转换为 RGBA。浏览器不允许将 VideoFrame 跨页面和扩展进程直接传递，因此只传递像素 ArrayBuffer；扩展 Worker 负责本机 WebSocket 传输。队列有限，拥塞时丢弃帧以避免持续累积延迟。

连接仅监听 127.0.0.1，使用随机 URL 令牌和来源校验。Native Messaging 端口负责连接寿命，关闭后释放共享内存。视频帧不落盘、不上传外部服务。原生捕获器校验尺寸、布局和格式，并在断流时撤除旧画面。

VSR 算法和强度保持原有设置。本次主要修正输入链路；更高强度、更换超分模型、长时间稳定 60fps 和音画同步仍需后续分别测量与比较。

参考：[WebCodecs 标准](https://www.w3.org/TR/webcodecs/)、[VideoFrame.copyTo](https://developer.mozilla.org/en-US/docs/Web/API/VideoFrame/copyTo)。
